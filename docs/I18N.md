# Making fireside speak another language

This covers the **website**. Book text, reader plugins and speech are untouched:
a Spanish interface still reads an English novel in the voice you picked.

## How it works

One JSON catalog per language in `ui/i18n/`:

```json
{
  "name": "Español",
  "dir": "ltr",
  "messages": { "Sign in": "Entrar", "Chapter {n}": "Capítulo {n}" }
}
```

**The key is the English sentence**, not an invented id. Two reasons: a
translator can work from a plain list without opening the page, and a missing
key degrades to English instead of showing `ui.lock.signin.title`. The cost is
that editing English wording orphans its translation, which is why
`tools/i18n_extract.py --check` reports catalog entries no longer present in the
page.

The host picks a language per request, in this order:

1. `?lang=es` - a shareable link that survives no cookies at all,
2. the `fs_lang` cookie the in-app switcher sets,
3. `Accept-Language`, with `q` weights and `es-MX` -> `es` fallback,
4. English.

`host/i18n.py` then rewrites `<html lang dir>` and splices the catalog in as
`window.__FS_I18N__` **before `</head>`**. Nothing is fetched after load, so the
page cannot paint English and then swap: the first paint is already the right
language. The catalog is JSON with `</` escaped, so a translation cannot close
the script tag.

## Marking a string

Static markup, either form:

```html
<button data-t>Sign in</button>
<h3 data-t="Plan &amp; storage">Plan &amp; storage</h3>
<input placeholder="Username" data-t-ph="Username">
<button title="Remove" data-t-title="Remove">
<button aria-label="Dismiss" data-t-aria="Dismiss">
```

The explicit attribute value matters when the text contains an entity
(`&amp;`): `el.textContent` decodes it and would not match the catalog key.

Scripts: `T('Sign in')`, `T('Chapter {n}', {n: 3})`. `T` returns the message id
when it has no translation.

## Adding a language

1. `cp ui/i18n/en.json ui/i18n/fr.json`, translate the values under `messages`,
   set `name` and `dir`.
2. Nothing else. The switcher lists whatever catalogs exist, from
   `/health`-adjacent `i18n.available()`, and picks the first paint language
   from the cookie.

RTL is automatic for `ar`, `fa`, `he`, `ur` (or set `"dir": "rtl"` explicitly).

## Checks

```
python3 tools/i18n_extract.py           # mark new static strings, refresh en.json
python3 tools/i18n_extract.py --check    # fail if a translatable string is unreachable
python3 -m unittest tests.test_i18n
```

`tests/test_i18n.py` holds the rules: negotiation order, q weights, junk
cookies, `dir`, catalog escaping, every marked key present in `en.json`, and no
hardcoded English left in the static page. The last one runs the extractor, so
a new `<p>Some sentence</p>` without `data-t` fails CI instead of quietly
becoming untranslatable.

## What is NOT covered yet

Strings the app draws from JavaScript (`toast(...)`, table cells, badges) are
still English literals. The runtime is in place and `T()` is global; converting
them is a per-call-site job, tracked as the remaining i18n work. `T` is
available in the app script's scope as a global, so the conversion is
mechanical.
